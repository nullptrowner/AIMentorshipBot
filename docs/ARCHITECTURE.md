# Архитектурные решения

## Границы

`bot/` — сообщения, кнопки и FSM. `application/` — транзакционные операции регистрации, заказов, платежей, подписок и подтверждённых административных изменений. `domain.py` — состояния, денежные величины, цены и правила лимитов. `infrastructure/` — внешние HTTP API, схема модели, файлы и криптографические проверки. `workers/` — внешний запуск, сверка, сохранение и доставка. `api.py` — HTTPS-входы и технические endpoints.

В Telegram callback передаётся только короткий идентификатор и действие. Владение заказом проверяется в прикладном сервисе. Административные операции повторно проверяют роль независимо от видимости кнопки. Одноразовое подтверждение содержит случайный nonce; финансовая операция использует этот nonce как ключ идемпотентности.

## Деньги

USD имеет точность шесть знаков; округление цены вверх определено в `money`. `user_balances.balance` включает резерв; доступно `balance - reserved`. Для изменений кошелёк блокируется через `SELECT FOR UPDATE`. Сумма всех ledger.amount восстанавливает баланс, сумма reserve_delta восстанавливает резерв. Журнал и платёжные события защищены от UPDATE/DELETE триггером. Исправление — отдельная компенсирующая операция с причиной.

Заказ фиксирует цену/оценку расходов/версию модели/шаблон/финальный промпт до подтверждения. Резерв создаётся вместе с очередью. Окончательное списание выполняется после сохранения результата, в одной транзакции с конечным статусом и задачей уведомления. Сетевой сбой проверки провайдера не является основанием для освобождения резерва. Для ошибки/подтверждённой отмены резерв освобождается ровно один раз.

Подписка содержит снимок условий плана. Её лимиты резервируются по модели, дате Москвы и корзине длительности. Параллельные подтверждения пользователя сериализованы его кошельком; счётчик дополнительно имеет составной первичный ключ. Изменение условий действующей подписки — явная административная операция. Создание новой подписки блокирует план, затем кошелёк в одном порядке.

## Очередь и сетевые границы

Для одного небольшого сервера выбран PostgreSQL outbox вместо дополнительного брокера: запись задачи и бизнес-операции атомарны. Воркеры забирают запись с SKIP LOCKED, назначают UUID владельца аренды, обновляют аренду каждые 20 секунд. Завершение проверяет владельца аренды. При падении запись снова доступна; recovery также сверяет незавершённые сущности. Ожидающие задания не размножают циклы polling при каждом sweep.

Платный POST создания prediction выполняется только после сохранённого намерения запуска. Если ответ неизвестен, автоматического повторного POST нет. Подписанный webhook может восстановить ID; иначе нужна сверка администратора. 429 допускает отложенный повтор отклонённого запроса. Для webhook Replicate проверяется исходное тело, timestamp и HMAC; сообщение служит сигналом к GET-сверке. События и транзакции дедуплицируются уникальными ключами.

Webhook Telegram сначала фиксируется в БД с уникальным update_id и получает ACK. Исключение — pre_checkout_query: на него нужно отвечать в пределах 10 секунд, поэтому он проверяется синхронно. Для одного invoice принимается один checkout, повтор того же query безопасен. Сообщения успешной оплаты обрабатываются и после утраты доступа сотрудником. Они не зависят от FSM.

## Файлы и инфраструктура

Пользовательские URL не принимаются. Скачивание результатов разрешено только с HTTPS-доменов replicate.delivery, с проверкой публичных IP и каждого redirect. Файлы пишутся потоком с ограничением размера. MIME определяется содержимым; изображения ограничены по пикселям, аудио/видео проверяются ffprobe. Декодерам запрещены сетевые протоколы и демультиплексоры плейлистов. Процессы ограничены временем, контейнер — памятью.

Подписанная ссылка содержит только случайный ID, срок и HMAC; endpoint выдаёт файл только при наличии активного заказа, использующего его. Нормализованные входы и выходы имеют отдельные сроки хранения. На старте сроки обязан выбрать владелец, чтобы случайно не включить бессрочное накопление на 30 ГБ.

Локальный volume — сознательный выбор для согласованного одиночного сервера. PostgreSQL/Redis/приложение допускают несколько процессов; несколько физических узлов требуют общего медиа-хранилища. Бэкапы должны храниться вне того же сервера. Секреты остаются в окружении, параметры бизнеса — в БД.
